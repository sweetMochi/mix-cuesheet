# Spec：mix-cuesheet 第一階段

Status: ready-for-agent

## Problem Statement

我在 YouTube 上聽 DJ 混音影片時，常常想知道裡面用了哪些原始曲目，以及每首在影片的第幾分幾秒開始。很多影片的說明欄沒有附曲目表，就算有也常常不完整或時間不準。現在只能自己拿手機開 Shazam，一邊拖曳進度條一邊辨識，一支一小時的混音要花很多時間，也很難整理成一份完整的曲目表

## Solution

一個只在自己電腦上執行的 Web App：貼上 YouTube 混音影片網址後，先顯示影片標題、長度和預估要辨識的片段數，確認後開始分析。系統會下載影片音訊，每隔固定時間切出一小段送去 Shazam 辨識，並把連續辨識到的同一首曲目合併成一列。分析過程中會即時顯示進度，辨識到的曲目也會一筆一筆出現在表格上。完成後可以看到每首曲目的開始時間、演出者、曲名、封面，點一下就能跳到 YouTube 該秒數確認，也能一鍵複製成可以直接貼到 YouTube 說明欄的純文字曲目表

## User Stories

1. 身為使用者，我想要貼上 YouTube 影片網址就能開始，這樣我不用手動下載任何檔案
2. 身為使用者，我想要貼上 `youtu.be` 短網址也能用，這樣我從手機分享出來的連結可以直接貼上
3. 身為使用者，我想要貼上帶有 `&list=` 參數的影片網址時，系統只處理那一支影片，這樣我從播放清單裡複製的網址也能用
4. 身為使用者，我想要在貼上純播放清單網址時看到明確的錯誤訊息，這樣我知道系統只支援單一影片
5. 身為使用者，我想要在貼上非 YouTube 網址或格式錯誤的網址時看到明確的錯誤訊息，這樣我知道要改貼什麼
6. 身為使用者，我想要在影片是會員限定、私人或需要登入時看到明確的錯誤訊息，這樣我知道問題出在影片本身而不是系統壞掉
7. 身為使用者，我想要在開始分析前先看到影片標題、長度和預估片段數，這樣我能確認貼對影片，也知道大概要跑多久
8. 身為使用者，我想要在影片超過 3 小時時被直接拒絕並看到原因，這樣我不會送出幾乎一定會被 Shazam 限流的超長任務
9. 身為使用者，我想要按下「開始分析」後才真正開始下載，這樣貼錯網址時不會浪費時間和頻寬
10. 身為使用者，我想要看到目前在哪個階段（下載中、切割中、辨識中），這樣我知道系統沒有卡住
11. 身為使用者，我想要在辨識階段看到「第 n／N 段」的進度和進度條，這樣我能估計還要等多久
12. 身為使用者，我想要辨識到的曲目即時出現在表格上，這樣我不用等整支影片跑完才看到結果
13. 身為使用者，我想要表格依開始時間排序，就算辨識請求是同時送出、回來的順序不一定，這樣表格才好閱讀
14. 身為使用者，我想要每一列顯示開始時間、演出者、曲名，這樣我能知道是哪首歌
15. 身為使用者，我想要每一列顯示小尺寸的專輯封面，這樣我掃一眼就能認出曲目；沒有封面資料時留白即可
16. 身為使用者，我想要每一列有 Shazam 連結，這樣我能進一步查看曲目資訊或找到串流平台
17. 身為使用者，我想要點開始時間就能在 YouTube 跳到影片的該秒數，這樣我能親耳確認辨識結果
18. 身為使用者，我想要每首曲目在曲目表中只出現一次，開始時間是整支影片中第一次辨識到的時間，這樣曲目表不會重複
19. 身為使用者，我想要同一首曲目在轉場時和其他曲目交替被辨識到，或播放途中有一段被誤判成別首時，仍然只列出一次，這樣轉場和誤判不會讓同一首歌重複出現
20. 身為使用者，我接受 DJ 真的重播同一首曲目時只列出第一次播放，因為在混音中重播的機率非常低
21. 身為使用者，我想要整支影片中只被辨識到一次的曲目仍然列出，但標記「僅命中 1 次」，這樣我知道它可能是誤判或很短的過場，可以自己去確認
22. 身為使用者，我想要連續 40 秒以上（2 個以上片段）沒有辨識到曲目的區段以「未辨識」列標出時間區間，這樣我知道曲目表哪裡有空缺，又不會被零星的辨識失敗干擾
23. 身為使用者，我想要一鍵複製 `00:00 Artist - Title` 格式的純文字曲目表，這樣我能直接貼到 YouTube 留言或說明欄
24. 身為使用者，我想要超過 1 小時的時間顯示成 `1:02:03` 格式，這樣長混音的時間戳記仍然能被 YouTube 辨識為可點擊的章節時間
25. 身為使用者，我想要在分析途中按「取消」就能停止任務，這樣貼錯影片或不想等時可以中止
26. 身為使用者，我想要取消或完成後，暫存的音檔都被刪除，這樣不會佔用我的硬碟空間
27. 身為使用者，我想要分析進行中時無法送出新的網址，這樣不會同時跑兩個任務互相拖慢或觸發限流
28. 身為使用者，我想要 Shazam 暫時限流時系統自動重試，這樣偶爾的限流不會讓整段結果遺失
29. 身為使用者，我想要重試多次仍失敗的片段被標成未辨識，而不是讓整個任務失敗，這樣我仍然能拿到其他片段的結果
30. 身為使用者，我想要下載失敗時看到明確的錯誤訊息，這樣我知道要不要更新 yt-dlp 或換一支影片
31. 身為使用者，我想要在電腦沒有安裝 yt-dlp 或 FFmpeg 時，看到明確指出缺少哪一個工具的錯誤訊息，這樣我知道要安裝什麼
32. 身為使用者，我想要介面使用繁體中文，這樣操作起來比較直覺
33. 身為使用者，我想要用一個啟動腳本就能開啟整個 App，只需要開一個網址，這樣平常使用時不用分別啟動前後端
34. 身為使用者，我想要 App 只綁定在 `127.0.0.1`，這樣區網裡的其他裝置無法存取
35. 身為使用者，我想要重新整理頁面後可以重新貼網址再分析一次，這樣任務出錯時能從頭來過
36. 身為開發者，我想要開發時用 `ng serve` 搭配 proxy 連到後端，這樣修改前端時有即時重新載入
37. 身為開發者，我想要取樣參數（片段長度、步距、長度上限、同時請求數、重試次數）集中在一個後端設定檔，這樣調整時只需要改一個地方
38. 身為開發者，我想要分析流程的核心邏輯可以注入假的音訊來源和辨識器來測試，這樣不用連網路也能驗證合併、重試、取消的行為

## Implementation Decisions

### 整體架構

- 後端使用 FastAPI，Python 3.14（已實測 shazamio 0.9.0 和 shazamio-core 2.0.0 在 Python 3.14 下可正常安裝與呼叫 Shazam API）
- 不使用 uv；以 Python 內建的 `venv` 建立虛擬環境，依賴以 `pip` 安裝，並在 `requirements.txt` 中以 `==` 鎖定確切版本；啟動腳本直接呼叫虛擬環境內的 Python，使用者不需要先手動啟用虛擬環境
- 前端使用最新版 Angular，採 standalone components 和 signals，不使用 UI 元件庫，自己寫 CSS
- repo 分為後端和前端兩個資料夾，根目錄放一個啟動腳本（使用者在 Windows 上，以 PowerShell 撰寫）
- 開發時前後端分開執行，`ng serve` 透過 proxy 把 `/api` 轉到 FastAPI；平常使用時由 FastAPI 直接提供 Angular build 後的靜態檔，只需啟動一個程序
- 後端只綁定 `127.0.0.1`，不做登入
- yt-dlp 和 FFmpeg 使用系統 PATH 上的版本，後端以子程序呼叫 CLI，不加入 Python 依賴；後端啟動時檢查兩者是否存在，缺少時健康檢查端點要回報缺少哪一個，前端顯示對應的錯誤訊息
- 介面文字一律使用繁體中文

### 領域用語

- **混音影片**：使用者輸入的 YouTube 影片
- **片段**：從混音影片音訊切出、送去辨識的一小段音訊，由起始秒數識別
- **辨識結果**：單一片段的辨識輸出，可能是一首曲目，也可能是無結果
- **曲目列**：曲目表中的一列，可能是一首曲目，也可能是一段未辨識區間
- **曲目表**：依開始時間排序的所有曲目列
- **分析任務**：從下載到產出曲目表的一次完整處理

### 設定常數（集中在後端單一設定模組）

- 片段長度：12 秒
- 取樣步距：20 秒
- 影片長度上限：3 小時（硬性上限，超過直接拒絕）
- Shazam 同時請求數：2～3（實作時取一個值）
- 遇到限流時的重試次數：3 次，指數退避

### 模組

**網址驗證（純函式）**
- 輸入使用者貼上的字串，輸出影片 ID 或具體的錯誤原因
- 接受 `youtube.com/watch?v=`、`youtu.be/`、帶 `&list=` 的影片網址（忽略清單參數）
- 拒絕純播放清單網址、非 YouTube 網址、格式錯誤的字串

**切段規劃（純邏輯，包含在任務執行器內）**
- 依影片長度、片段長度、步距算出所有片段的起始秒數：從 0 開始，每隔一個步距一段，直到起始秒數超過影片長度
- 最後一段的長度取「片段長度」和「剩餘長度」的較小值；剩餘長度太短（少於 5 秒）的最後一段直接略過
- 預估片段數與實際切段使用同一套計算，確保確認畫面上的數字和進度條的 N 一致

**合併規則（純邏輯，包含在任務執行器內）**
- 前提：在使用情境中，同一首曲目在一支混音裡重複出現的機率非常低，所以同一首曲目的多次命中一律視為同一次播放
- 以 Shazam 回傳的曲目識別碼判斷是否為同一首
- 每首曲目在曲目表中只出現一次：整支影片中所有命中同一首的片段都併入同一列，開始時間取最早一次命中的片段起始時間；不論中間隔了多少無結果片段或其他曲目都一樣（這同時處理了轉場時兩首交替被辨識，以及播放途中被誤判成別首的情況）
- 整支影片中總命中次數只有 1 次的曲目列仍然保留，並加上「僅命中 1 次」標記
- 「未辨識」列與曲目無關，只看無結果片段本身：連續 2 個以上的無結果片段合併成一列「未辨識」；單一個無結果片段一律忽略
- 「未辨識」列的時間區間從該段第一個無結果片段的起始時間，到緊接在最後一個無結果片段之後的片段起始時間（或影片結尾）
- 曲目表中的曲目列與「未辨識」列一起依開始時間排序
- 尚未完成辨識的片段視為「待處理」，不能當成無結果，也會中斷連續無結果片段的計算；即時曲目表只根據已完成的辨識結果計算，並在每次有片段完成時重新計算整份曲目表

**分析任務執行器（主要測試接縫）**
- 輸入：影片資訊（ID、長度）、設定常數、一個音訊來源、一個辨識器、一個取消信號
- 輸出：一連串事件
  - 階段變更：下載中、切割中、辨識中
  - 辨識進度：已完成數 n 和總數 N
  - 曲目表快照：每次有片段完成辨識時，送出依目前結果重新計算的完整曲目表
  - 完成：最終曲目表
  - 錯誤：錯誤原因（例如下載失敗）
  - 已取消
- 辨識請求以有上限的並行度送出；辨識器回報限流時以指數退避重試，用完重試次數，或遇到其他辨識錯誤時，該片段視為無結果，任務繼續執行
- 退避的等待機制要能注入，讓測試不需要真的等待
- 收到取消信號時，停止送出新的請求、中止進行中的子程序，並送出「已取消」事件
- 不論完成、錯誤或取消，任務專屬的暫存資料夾都要刪除

**音訊來源（介面加實際實作）**
- 介面：準備好整支影片的音訊，以及依起始秒數和長度產出一個片段檔
- 實際實作：以 yt-dlp 下載最佳音質的音訊到任務暫存資料夾，再以 FFmpeg 依時間切出片段（單聲道，取樣率以 Shazam 可接受的範圍為準）
- 下載失敗時要把 yt-dlp 的錯誤轉成使用者看得懂的訊息（例如會員限定、私人影片、影片不存在）

**辨識器（介面加實際實作）**
- 介面：輸入一個片段檔，回傳辨識到的曲目（識別碼、演出者、曲名、Shazam 連結、封面網址，封面可能為空值）或無結果；限流時丟出可辨別的限流錯誤
- 實際實作：使用 shazamio；要正確關閉底層的 HTTP session，避免出現 Unclosed client session 警告

**曲目表文字輸出（純函式）**
- 輸入曲目表，輸出可貼到 YouTube 的純文字，每行 `時間 Artist - Title`
- 時間格式：未滿 1 小時用 `MM:SS`（例如 `00:00`、`12:40`），1 小時以上用 `H:MM:SS`（例如 `1:02:03`）
- 「未辨識」列不輸出；「僅命中 1 次」的曲目照常輸出，不加標記
- 這個函式放在後端並納入 pytest；前端顯示的時間格式要和它一致（可以由後端在曲目表中直接附上格式化後的時間與純文字，前端不重複實作）

### API 契約

- **健康檢查**：回傳 yt-dlp 和 FFmpeg 是否可用
- **預先解析影片**：輸入網址；成功時回傳影片 ID、標題、長度（秒）、預估片段數；失敗時回傳錯誤原因（網址無效、播放清單、影片無法存取、超過長度上限），超過上限時也一併回傳影片長度讓前端顯示
- **建立分析任務**：輸入影片 ID；回傳任務 ID；已經有任務在執行時回傳衝突錯誤
- **任務事件串流**：SSE，依序推送上面列出的事件類型；前端用 EventSource 接收並轉成 signals
- **取消任務**：刪除指定的任務
- 同一時間只允許一個分析任務；不做任何結果快取，每次都重新下載與分析

### 前端畫面與狀態

- 狀態流程：輸入網址 → 解析中 → 確認（顯示標題、長度、預估片段數，並有「開始分析」按鈕）→ 分析中（階段文字、進度條、即時曲目表、「取消」按鈕）→ 完成／錯誤／已取消
- 分析中停用網址輸入和送出按鈕
- 曲目表欄位：封面縮圖、開始時間（連到 YouTube 的 `&t=<秒數>s`）、演出者、曲名、Shazam 連結；「僅命中 1 次」以標記顯示；「未辨識」列顯示時間區間
- 「複製曲目表」按鈕把後端產生的純文字複製到剪貼簿，並給出已複製的提示

### Git

- 在現有資料夾直接執行 `git init`（不要刪除 `.git` 內 Fork 的設定檔），並加上適用 Python（含虛擬環境資料夾）與 Angular 的 `.gitignore`

## Testing Decisions

- 好的測試只透過模組對外的介面驗證行為：給定輸入，檢查輸出的事件和曲目表，不檢查內部的資料結構、呼叫順序或私有函式
- 使用 pytest；這是全新的 repo，沒有既有的測試可以參考
- **分析任務執行器**（主要接縫）：注入假的音訊來源和假的辨識器（例如「片段 0～3 回傳曲目 A、片段 4 無結果、片段 5 先丟限流錯誤再回傳 A」），以及立即返回的退避等待，驗證：
  - 切段數量與起始時間，包含最後一段太短被略過的情況
  - 連續命中合併、開始時間取第一次命中
  - 同一首被無結果片段或其他曲目隔開後再出現時，仍只有一列，開始時間取最早一次命中（例如 A、A、B、A、B、B 只產生 A 和 B 兩列）
  - 只命中 1 次的標記以整支影片的總命中次數判斷
  - 單一個無結果片段不產生「未辨識」列，連續 2 個以上才產生，且時間區間正確
  - 限流後重試成功；重試用完後視為無結果，任務仍正常完成
  - 辨識結果亂序完成時，曲目表快照仍依時間排序，且待處理的片段不會被當成未辨識
  - 取消後送出「已取消」事件且不再呼叫辨識器
  - 音訊來源丟出下載錯誤時送出錯誤事件
  - 完成、錯誤、取消後暫存資料夾都被刪除
  - 進度事件的 N 與預估片段數一致
- **網址驗證**：各種合法網址都能取出正確的影片 ID；播放清單、非 YouTube、格式錯誤的輸入回傳對應的錯誤原因
- **曲目表文字輸出**：時間格式（未滿 1 小時、剛好 1 小時、超過 1 小時）、「未辨識」列被排除、「僅命中 1 次」照常輸出
- 不寫自動化測試的部分：真實的 yt-dlp 下載、FFmpeg 切割、Shazam 呼叫，以及 Angular 前端；這些以實際跑一支混音影片手動驗證

## Out of Scope

- 在介面上調整片段長度與步距（第二階段）
- 在換歌邊界附近以較小步距細掃、提高時間精度（第二階段）
- 以音量或能量變化偵測換歌點的辨識策略
- 結果快取（每次都重新分析）
- 保留下載的音檔
- CSV／JSON 等檔案匯出
- 前端自動化測試
- 打包成安裝檔或桌面應用程式

## Further Notes

- shazamio 使用的是非官方 Shazam API，隨時可能被限流或改版；辨識器介面的設計讓之後替換實作時，不需要動到任務執行器
- yt-dlp 需要經常更新才能跟上 YouTube 的變動；下載失敗的錯誤訊息可以提示使用者先更新系統上的 yt-dlp
- 時間精度等於取樣步距（20 秒）；第二階段的細掃功能就是為了改善這一點
- 每首曲目只出現一次的代價：DJ 真的重播同一首時，第二次播放不會列出；依使用情境這個代價可以接受
- 以下細節在需求訪談中沒有明確討論，本 spec 採用合理的預設值，實作時如果發現不合適可以提出：最後一段少於 5 秒時略過、複製的純文字不包含「未辨識」列
- 「未辨識」的門檻為連續 2 個片段（約 40 秒），已與使用者確認
